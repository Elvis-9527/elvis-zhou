# 钉钉文档的真相是块结构

半年前，我想把一个 AI 生成的会议纪要导入钉钉文档。本来以为 20 分钟的事。

结果花了 2 天。

不是因为 AI 写不好，而是因为我没理解**钉钉文档的真实结构**。

## 表面问题 vs 深层问题

最开始我以为问题很简单：
- AI 生成 Markdown 格式的内容
- 转成 HTML 或其他什么
- 贴进钉钉文档

在直接操作文档结构时，不能把 Markdown 或 HTML 当成接口载荷直接提交，需要适配目标接口的**块结构（block-level structure）**。导入能力与结构编辑接口要分开看。

一个看起来简单的"段落"，可以用下面的概念结构说明（并非可直接提交的钉钉接口格式）：

```json
{
  "type": "paragraph",
  "attrs": {
    "align": "left",
    "indent": 0
  },
  "content": [
    {
      "type": "text",
      "text": "这是一段内容",
      "marks": [
        {
          "type": "strong"
        }
      ]
    }
  ]
}
```

这不是 Markdown 的 `**这是一段内容**`，也不是 HTML 的 `<strong>这是一段内容</strong>`。

这是一个**嵌套的、有类型标注的数据结构**。

## 为什么 AI 写不进去

我最初的方案：AI 生成 Markdown → 用开源库转成 JSON → 贴进钉钉。

问题是：
1. **开源库的 JSON 格式和钉钉的格式不匹配**。那个库可能生成 `{"type": "paragraph", "text": "..."}`, 而目标结构可能要求 `{"type": "paragraph", "content": [...], "attrs": {...}}`。细节差异很大。

2. **AI 生成的内容经常有"人类写法"，但钉钉结构不支持**。比如：
   - 我想要一个"标题加缩进"的效果（看起来像树形）
   - Markdown 可能写成 `# 标题\n  - 子项`
   - 但钉钉要求显式的 `indent` 属性
   - AI 不知道这个属性的存在，所以生成的 JSON 就不能正确渲染

3. **格式化和样式的映射很复杂**。比如：
   - 某个公司的钉钉模板要求"会议主题"用绿色背景
   - "核心决议"用红色加粗
   - AI 生成的内容不知道这些约定，结果贴进去就格式混乱

## 真正的解决方案

我后来写了一个转换工具：`md2jsonml`。

关键的转变是：**不再试图通用转换，而是针对钉钉文档的结构设计专属的 Markdown 变种**。

### 设计的核心逻辑

#### 1. 定义"钉钉友好"的 Markdown

不是标准的 Markdown，而是一个**受限的子集**，里面的每一个符号都能 1-1 映射到钉钉的块结构：

```markdown
# 标题1
## 标题2
### 标题3

这是普通段落。

> 这是引用（对应钉钉的 callout 块）

- 列表项 1
- 列表项 2

**加粗文本**
*斜体文本*
`代码片段`
```

每一种语法，都提前定义好对应的钉钉 JSON 结构。

#### 2. 用映射表来处理特殊符号

```javascript
const DINGDING_BLOCK_TYPES = {
  'h1': { type: 'heading', level: 1, ... },
  'h2': { type: 'heading', level: 2, ... },
  'h3': { type: 'heading', level: 3, ... },
  'paragraph': { type: 'paragraph', align: 'left', "indent": 0 },
  'bulleted_list': { type: 'bulletList', ... },
  'ordered_list': { type: 'orderedList', ... },
  'quote': { type: 'callout', style: 'info', ... },
  'code': { type: 'codeBlock', language: 'text', ... },
}
```

上面是映射思路的伪代码；实际字段和支持范围应以所用接口文档为准。

#### 3. 处理嵌套和缩进

嵌套和缩进的表达要按具体接口适配，不能直接套用 Markdown 的树形结构。下面用转换器的中间结构示意：

我在转换时增加了一个步骤：
```markdown
- 一级项
  - 二级项
  - 二级项
- 一级项
```

转换成：
```json
[
  { "type": "bulletList", "content": "一级项", "indent": 0 },
  { "type": "bulletList", "content": "二级项", "indent": 1 },
  { "type": "bulletList", "content": "二级项", "indent": 1 },
  { "type": "bulletList", "content": "一级项", "indent": 0 }
]
```

#### 4. 样式和元数据的注解

对于需要特殊格式的部分，用注解来标记：

```markdown
{type: decision, color: red}
这是一个核心决议，要用红色高亮。

{type: action, owner: 张三, deadline: 2026-11-15}
- 张三负责完成 API 文档
```

转换时，这些注解被解析为钉钉的特殊块属性。

### 转换工具的架构

```
输入（Markdown 变种）
  ↓
解析器（Tokenize）
  ↓
AST（抽象语法树）
  ↓
验证（检查是否符合钉钉的块约束）
  ↓
代码生成（从 AST 生成钉钉 JSON）
  ↓
输出（钉钉 docJSON 或直接 API 调用）
```

关键是中间有一个**验证步骤**。在代码生成前，检查：
- 有没有不支持的嵌套？
- 有没有超长的行？
- 有没有不支持的符号？

如果有问题，提前报错，而不是生成一个"看起来可以但贴进去就乱"的 JSON。

## AI 在这个过程中的角色

现在，有了这套工具，AI 的工作变清楚了：

### AI 的职责
1. **理解会议内容**，生成**钉钉友好的 Markdown**
2. 不用生成 JSON、不用处理复杂的块结构
3. 遵循特定的 Markdown 语法规范（因为只有这些符号会被正确转换）

### 示例 prompt 给 AI

```
生成会议纪要，用以下格式：

# 会议主题

## 参会人员
- 张三（主持）
- 李四

## 核心讨论
以段落形式记录讨论内容。遇到重要决议或待办，用以下格式：

{type: decision}
【决议内容】

{type: action, owner: 责任人, deadline: YYYY-MM-DD}
- 具体任务描述

## 下次会议
【时间和主题】

规范：
- 此转换器示例暂不处理表格，表格需单独适配
- 不要用多级缩进超过 3 层
- 不要生成自定义的 HTML 或 Markdown 扩展
- 使用上面定义的格式标记关键内容
```

这个 prompt 能减少格式偏差，但生成后仍需要验证结构，并检查写入后的实际显示。

## 这个经历的启示

### 1. 界面是表象，块结构才是真相

很多人看到"钉钉文档"，以为那就是一个"文本编辑器"。

不同文档工具有各自的**结构化文档模型**。JSON、JSONML 等是接口可能使用的表达形式，不能把它们与编辑器内部存储直接等同。

要做好内容生成和转换，必须**理解底层的块结构**，而不是试图"在上层"做转换。

### 2. 适配不是转换

我最初的想法是"转换"：Markdown → 钉钉 JSON。

但实际上，问题在于两边的语法体系完全不同。所以不是"转换"，而是**重新设计一个中间格式，两边都能理解**。

这个中间格式（钉钉友好的 Markdown）成了新的"标准"。

### 3. 约束是特性

有了钉钉友好的 Markdown 约束以后，看起来好像"限制"了 AI 的表达能力。

但实际上，这些约束让一切都变清晰了：
- AI 知道自己不能做什么
- 工具知道自己要处理什么
- 用户知道最后会得到什么

反而提升了成功率。

## 实战建议

如果你需要自动化地向某个工具（钉钉、Notion、飞书等）写入内容：

### 1. 先研究目标工具的块结构

不要试图通过界面来"反向工程"。直接看文档或 API：
- 有哪些块类型？
- 怎么表达嵌套？
- 有哪些属性（样式、对齐、缩进等）？

### 2. 设计一个"中间格式"

这个格式应该：
- 是一个受限的 Markdown 或类 Markdown 变种
- 每个符号都能 1-1 映射到目标工具的块结构
- 足够强大来表达你需要的内容，但足够简单来易于处理

### 3. 把格式的规范写进 AI 的 prompt

不要指望 AI 自己猜。明确告诉它：
- 用什么符号表达标题
- 用什么符号表达列表
- 哪些格式不支持
- 有哪些特殊注解（比如 `{type: decision}`）

### 4. 实现一个验证层

在生成最终的 JSON 前，检查中间格式有没有被正确遵循。提前发现问题，比等到贴进钉钉后再崩溃要好得多。

## 最后的想法

这个项目教会了我一个教训：**不要试图"通用"解决问题，要深入理解具体系统的设计，然后在理解的基础上做适配**。

很多工具集成失败，表面上看是"格式不对"，深层的原因通常是没有真正理解目标系统的设计哲学。

一旦理解了，反而会发现：约束越清晰，解决方案越简单。

甚至，AI 的工作反而会更出色——因为它知道界限在哪里。
